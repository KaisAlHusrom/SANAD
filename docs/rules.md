# Sanad Tech — Rules (binding law)

> **These rules are append-only living law.** They are MUST/NEVER, greppable by ID, and specialized to this project (Nx · NestJS microservices · RabbitMQ · per-service Postgres · Next.js website · React/Vite portals · **Arabic-default** RTL · `APP_ENV`).
>
> **Legend:** **MUST** = always do. **NEVER** = never do. Each rule has a stable ID (`U1`, `N3`, `MS2`…). When you fix a bug or hit a recurring mistake, **add a rule** and a dated entry to the change-log at the bottom — never silently break a rule; change it explicitly.
>
> **⚠️ Standing directive — we are building the FINAL product, NOT an MVP.** `docs/plans/02-mvp.md` is a **filename**, not a quality bar. **NEVER** justify a narrower scope, a weaker surface, a stand-in component, or a deferred axis with "it's the MVP" / "good enough for now" — that framing is retired. Every phase ships its scope finished on every axis (U21), and a cross-cutting gap is fixed **platform-wide**, never patched only where it was noticed. Needs another session to do properly → **split the work, never lower the bar**. (Owner directive, 2026-07-20.)

## U — Universal (every app, every stack)

- **U0 PERFECTION IS THE REQUIREMENT — THIS RULE OUTRANKS EVERY OTHER RULE IN THIS FILE.**
  Owner's standing directive, 2026-07-30, verbatim: _"I always want the most perfect, advanced and
  user friendly ui/ux result for each simple feature in this project, I don't want to build anything
  simply or just to finish the task, even if this will take so time, or the one phase will be divided
  to 10 phases, I don't mind, my priority is the perfect result."_
  - **NEVER** ship a surface that merely works. Every feature — however small, however internal — gets
    the most advanced, most user-friendly UI/UX the design language allows. "It functions" is not a
    finished feature; "it is a joy to use" is.
  - **NEVER** render a raw JSON textarea, a bare key/value grid, a free-text box, or any other
    lowest-common-denominator control where the domain has a known shape or a known set of values. A
    structured domain gets a **purpose-built structured editor**, or it is handed to the module that
    owns it — it does **NEVER** get a blob and a shrug.
  - **A phase is a unit of scope, not a unit of time.** If a phase cannot be built to this standard in
    one pass, **SPLIT IT** into as many phases as it takes. Ten phases for one feature is **correct**;
    one rushed phase covering four surfaces is a **defect**. **NEVER** compress scope into a single
    session in order to "finish" — the plan is the place to divide work, and dividing it is expected,
    not a failure.
  - Every screen ships **ALL** of its states: loading, empty, error, read-only, permission-denied,
    long-content, ar-RTL **and** en-LTR, dark **and** light, at phone / tablet / desktop widths. A
    missing state is an **unfinished screen**, not a follow-up.
  - Every overlay, list, table and pane **contains its own content**: nothing clips, nothing escapes
    the viewport, nothing scrolls the page behind it, and every scroller wears the product's own
    design — never the raw platform default.
  - **"The tests pass" is NOT "it is done".** Boot it, open it, look at it in both directions and both
    themes, and only then check the phase off. A green gate is the floor, not the finish line.
  - When speed, convenience, or the wish to close a phase conflicts with quality: **quality wins.
    Always. Without discussion.**
    U21 (every axis) and U23 (every state) are the _implementation_ halves of this rule and defer to it;
    U28 is its decision half; U11/U13 say where divided scope is recorded. (Owner directive re-stated to
    this repo 2026-08-08.)

- **U1 — Module/service isolation.** Each feature is a self-contained module; it **NEVER** imports another module's internals. Cross-module/-service communication goes through a **typed bus** (backend: RabbitMQ events + request/reply; frontend: the client event bus + shared lookup apis). See MS1–MS3, N6.
- **U2 — Shared code lives in `libs/` only.** Anything used by 2+ modules/services lives in a `libs/*` package. A `libs/shared/*` package **NEVER** imports from an app or a feature module.
- **U3 — Single source of truth.** Never define the same type/contract/constant/logic twice. **All API + message contracts live once in `libs/contracts`** (Zod schemas + `z.infer` types), imported by every service and frontend. No duplicated DTO shapes.
- **U4 — No `any` / no `unknown`.** Explicit `type`/`interface` (or `z.infer`) for every entity, DTO, arg, return, prop, slice, message payload. Strict tsconfig (`strict`, `noUncheckedIndexedAccess`, `noImplicitReturns`, `noUnusedLocals`, `noUnusedParameters`). **NEVER** `as any` / `@ts-ignore` to silence the compiler — fix the type.
- **U5 — Logic in hooks/services; the surface is thin.** Frontend: a component's logic (state, effects, fetching, handlers, derived values) lives in a co-located `use-*` hook; the component body is presentation-only. Backend: controllers/message-handlers are thin; logic lives in application services.
- **U6 — Design tokens only.** **NEVER** hardcode colors/spacing/radius/typography/shadows/z-index. Missing value → add it to the token system FIRST, then use it. **Theme scope:** the two **dashboards** support **dark + light**; the **website** is a **single fixed signature theme** (no toggle — WEB7). (Carve-out: genuine runtime data — a chart bar width, a canvas/WebGL coordinate — may be an inline style, marked with a comment.)
- **U7 — Full RTL / direction correctness.** Use logical properties (`start`/`end`, `ms-`/`me-`, `inset-inline-*`), never `left`/`right`. Mirror directional icons. Derive physical sides (Radix `side`, drawer slide direction) from the active direction. **Arabic is the default → RTL is the default**; LTR is the special case.
- **U8 — i18n.** All user-facing strings come from per-module i18n catalogs in **`ar` (default) and `en`**; **identical key trees across both locales** (verifier-enforced parity). Translatable _content_ comes from the API/settings, never hardcoded. Language names are endonyms (العربية / English).
- **U9 — Settings-with-defaults.** Every admin/client-configurable value (branding, colors, logo, locale, feature toggles…) resolves **scope-override → global value → coded default**. The coded default is returned when unset so the product never renders blank. **NEVER** hardcode one configuration inline.
- **U10 — One concept per file.** Each enum/type/schema/constant-group is its own kebab-case file; `index.ts` is a **re-export barrel only**.
- **U11 — Plans before building; PROGRESS is the ledger.** Read `docs/plans/*` + `docs/PROGRESS.md` before any work; build in `02-mvp.md` phase order; **every session updates `PROGRESS.md`** (done / next / decisions / issues).
- **U12 — Always verify, in two tiers.** Pre-commit/pre-push hooks are **NEVER** bypassed (`--no-verify` forbidden). Verification has exactly two tiers, and confusing them is the violation:
  **(a) Mid-phase**, after each work chunk: `nx affected -t typecheck lint test --base=<sha at phase start> --parallel=2`. Same targets, scoped to what changed. Use this freely — it is the working gate.
  **(b) Phase-closing**, before a phase may be marked `- [x]`: the **verifier** agent running the FULL `nx run-many -t typecheck lint test build --parallel=2` with the stack **DOWN**, then the **boot-verifier** agent with the stack UP (U29). Both must be green.
  **NEVER** mark a phase done on tier (a) alone, and "pre-push passed" is NEVER "verifier passed" — pre-push only checks what the push _affects_ (OPS4). The closing gate is unchanged from the original U12; only the mid-phase repeats were scoped. (Owner decision, 2026-08-15: the full matrix was being re-run for every one-line `/fix`.)
- **U13 — Rules stay lean; add one only for a genuinely cross-cutting constraint.** This file is **binding law read every session** — its value is that it's short enough to actually follow, so it must NOT grow with per-session noise. A one-off bug fix, a local gotcha, or "what I did this session" goes in **`PROGRESS.md`** (and memory), **never here**. Add a rule ONLY when the lesson is **reusable and platform-wide** — it will recur across features and its absence would cause the same class of mistake again; when unsure, **ask** rather than append. No per-session change-log ceremony. Never silently break a rule; change it explicitly. (Owner directive, 2026-07-25: the file was bloating from a rule-per-session habit — reversed.)
- **U14 — No secrets in code; env-based config.** All secrets via env. Reference projects are read-only patterns — **NEVER** import from them.
- **U15 — Verify shapes, never invent them.** Before defining any type/DTO representing data crossing a boundary, **verify the canonical shape against the source of truth** (the Drizzle schema, the service's actually-returned object, the message contract) and cross-check an existing consumer. **NEVER** fabricate a field — the compiler accepts invented shapes and runtime then fails silently. New endpoint/message → contract-typecheck pass FIRST.
- **U16 — Validated shapes are Zod-first, file-name split.** Anything validated at runtime (request body, query/params, form input, message payload) is a **Zod schema**; its type is `z.infer`. Runtime-validated schemas+types → `*.zod.types.ts`; non-validated shapes (response DTOs, route/nav params, literal unions) → `*.types.ts`. **NEVER** duplicate a shape between a schema and a hand-written interface.
- **U17 — Modules own features; infrastructure is shared (litmus).** Before placing a hook/component/util/type in a feature module, ask: _"would a future, unrelated module need this?"_ If yes → it's infrastructure, it lives in `libs/`, regardless of which feature first surfaced it. Generic request shapes (query/filter/sort/pagination) are **always** shared.
- **U18 — Every constant has a home; no bare inline literals.** A reusable design number → a **token**. A component-private number (card width, TTL, placeholder count) → a colocated `<thing>.constants.ts`. **NEVER** a bare numeric literal inline (allowed: `0`, `1`, platform-required exacts).
- **U19 — One typed env accessor (`APP_ENV`).** Env values are read through **one** typed accessor module per app (`env.ts` / `Env`), never raw `process.env` / `import.meta.env` at call sites (enforce with `no-restricted-imports`). **All environment branching uses `APP_ENV` (`development`|`staging`|`production`), never `NODE_ENV`.** The accessor validates at startup and **fails fast** on a missing required key; it supplies a production fallback per public key so a mis-built release still reaches the real backend.
- **U20 — Group files by kind into typed subfolders; never a flat dump.** Inside any module/lib/app area, files are organized into **kind-named kebab subfolders** — `guards/`, `decorators/`, `interceptors/`, `filters/`, `pipes/`, `verifiers/`, `strategies/`, `controllers/`, `services/`, `repositories/`, `schema/`, `events/`, `consumers/`, `helpers/`, `types/`, `constants/`, `hooks/`, `components/`, … — **NEVER** a single directory mixing many kinds. Each subfolder has an `index.ts` **re-export barrel** (U10), and the parent re-exports the subfolder barrels. This holds for **every app and every microservice**, on top of the backend DDD layering (N4: presentation/application/domain/infrastructure) and the frontend module layout (F-rules) — group by kind _within_ each layer. A subfolder with a single file today still gets its kind folder, so growth never forces a reshuffle. Litmus: if two files in one directory would answer "what kind of thing is this?" differently, they belong in different subfolders. **(Amended 2026-08-08: U20 says which kind-folder a file belongs in; **U26** says what its home looks like once it is there — a logic unit is a folder holding its source **and its spec**, a declaration file sits loose in its kind folder.)**

- **U22 — A form's schema validates EXACTLY the fields it renders; a blocked submit is NEVER a silent no-op.** A config/`DynamicForm`'s Zod schema MUST accept the exact default values the form seeds for the fields it renders — a required key the form never renders (a hidden `translations.<locale>.<field>`, an `imageMediaId` for a kind with no image picker) makes `react-hook-form`'s `handleSubmit` abort **before** the mutation, attaching the error to an **unrendered** field → the user clicks Save and **nothing happens, no toast**. So: keys the form omits per variant are `.optional()` (tolerate `undefined`), the schema derives its translatable/optional keys from the SAME source the field list does, and `handleSubmit` MUST pass an **`onInvalid`** that surfaces a generic error toast + root error (never swallow an invalid submit). Verify by driving the ACTUAL seeded defaults through the schema (not hand-passed values that mask the gap).

- **U21 — Ship every axis to the same bar; no weak sides (design, interaction, and polish are not optional).** Correct logic/architecture is **half** the work — a feature is **not done** until its **interface and interaction are finished to the same standard**. Concretely: **(a) Build to the locked design canon.** Every portal/website surface MUST match `docs/design/` (`design-spec.md` tokens + shell + the `source/*.dc.html` references) in **look AND feel**. When a design for the exact screen exists, build to it; when it doesn't, **derive** from the nearest reference + the spec — **NEVER** invent a thinner/weaker look. **(b) Proper components, never raw placeholders.** **NEVER** ship a bare HTML control (`<select>`, unstyled `<input>`, default checkbox) or a "minimal" stand-in where the design specifies a real component — build the styled token/Radix/shadcn component **first** (F9), reused app-wide (a real Select with a styled popover, etc.). **(c) Overlays size and scroll gracefully.** Modals/dialogs/drawers MUST have a comfortable width for their content, **cap their height and scroll their body internally** with a **sticky header + action footer** — never a cramped, full-height, unscrollable box. **(d) Every field, table, pill, badge, empty/skeleton/error state** follows the design's spacing, radius, focus ring, typography, and tone. **(e) Verify by looking.** "Tests pass" does not mean done — **run the app and view the surface**; it is done when a reviewer opens it and it reads as **finished and on-design**, needing no follow-up edits. **(f) Same care, big or small** — a one-line cell, a filter dropdown, a toggle: each gets the same attention as the headline feature. **If perfecting an axis needs another session, split the work — NEVER lower the bar to finish faster.** Applies to every phase and every component. (Plans MUST cover the design/interaction axis explicitly, not just logic — U11.)

- **U23 — Every surface ships ALL of its states; a state you didn't design is a bug you shipped.** Building a screen, component, hook, action, or endpoint means building **every state it can be in**, not only the happy path: **loading** (content-shaped skeleton, F2), **empty** (first-use vs. no-results vs. filtered-to-nothing — each with its own copy and its own next action), **error** (the _real, actionable_ reason plus a retry/fix affordance — never a dead end), **partial/degraded** (offline, a dependency 503, a permission the user lacks, stale cache), **in-flight** (pending, per-item progress, disabled/optimistic), and **edge data** (zero, one, very many, very long text, ar **and** en). **NEVER** ship an action that can fail without telling the user it failed — a click that produces no visible outcome is the worst possible state, and _"the mutation exposes an error the component never reads"_ is exactly that. Concretely: **(a)** every mutation surfaces success **and** failure (toast + inline, where the action lives), and the message **names the cause** — never a bare `Something went wrong`; **(b)** every `catch` either handles or surfaces — an empty or comment-only `catch` is a rule violation; **(c)** an error the user _can_ fix MUST offer the fix (button/link); one they cannot MUST say who can; **(d)** the states are **enumerated in the plan before the code**, and each is **verified by looking** (U21e) — a green test suite is not proof a state renders. This applies to the smallest control as much as to the headline feature, and it is the companion of U21: U21 says finish every _axis_, U23 says finish every _state_ of each. (F2/F3 are the list-specific case of this rule; U22 is the form-specific case.)

- **U24 — Every user-facing backend message is a localized KEY, never prose; the locale travels with the request.** The backend is **Arabic-first exactly like the frontend** (U8): a response's `message`, an error's text, and any message-shaped field **inside** a payload MUST render in the locale the caller selected. Therefore: **(a)** a service **NEVER** emits user-facing prose — it emits a stable **`messageKey` + `params`** (`rpcError(status, key, params)` / `httpError(...)` from **`@sanad/i18n`**), and the message _text_ lives **only** in that lib's `ar`/`en` catalogs with **verifier-enforced key parity** (U8); **(b)** the **gateway edge is the only renderer** — the response interceptor and the exception filter translate the key once, using the request locale, so no controller ever formats a message; **(c)** the locale is carried by the header **`x-sanad-locale`**, resolved **`x-sanad-locale` → `accept-language` → `ar`**, attached by **each frontend's single header place** (F1) and forwarded gateway→service in the **RMQ headers** next to the identity (MS4); **(d)** text that is part of the **payload** rather than the envelope (an integration test result, an email body, a notification) is translated **in the service** from that forwarded locale — it never reaches the client in English; **(e)** a **third-party/vendor** error message (AWS, SMTP, a payment gateway) is surfaced as a **localized line + the raw technical text in a separate `detail` field**, never as the message itself; **(f)** internal invariant throws (`insert returned no row`) stay English and MUST NOT be user-visible — they surface as the localized generic 500. **NEVER** hardcode an English string into a response, and **NEVER** "fix" a translation only on the screen where it was reported — the key belongs in the catalog for every service. New service/endpoint → its keys go in the catalog **before** the handler.

- **U25 — A shared component that can open inside a modal/portal must not assume router (or any host) context.** The admin's `GlobalModalManager` is mounted **beside** `RouterProvider`, not inside it, so a form-opened picker has **no router context** — react-router hooks (`useSearchParams`/`useLocation`/`useNavigate`) throw there and blank the app. So a portal-able component reads/writes the URL via **`window.history`/`window.location`** (use `history.replaceState` for state that only _mirrors_ into the URL) or takes what it needs by prop, and its **modal/picker** test renders it **without** a router — a `MemoryRouter` wrapper hides the crash from the suite (and it's invisible to typecheck), so it only shows up live (U21e).

- **U26 — A logic unit is a FOLDER holding its source and its spec; a declaration file is not.** This is the _leaf_ law under U20 (which says what kind-folder a file belongs in) — U26 says what the file's own home looks like once it gets there. Any file that carries **logic** — service, controller, repository, mapper, validator, seeder, resolver, consumer, guard, strategy, interceptor, pipe, filter, registry, adapter, util, and on the client every `use*` hook, slice, and component — lives in a folder named after the **concept** (the basename minus the role suffix), holding the source **+ its `*.spec.ts(x)` + any `*.types.ts` + an `index.ts` barrel**: `application/services/roles/{roles.service.ts, roles.service.spec.ts}`, `hooks/use-client-list/{use-client-list.ts, use-client-list.spec.ts, index.ts}`. This holds **whether or not the spec exists yet** — a one-file folder is the TDD1 debt made _visible_ instead of buried, and it means writing the spec later never forces a second move. **Declaration-only** files (`*.types.ts`, `*.zod.types.ts`, enums, tables, events, errors, tokens, definitions) sit **directly** in their kind folder — many of one role together is correct. **NEVER** a central `tests/` / `__tests__/` / `spec/` tree, and **NEVER** a directory of many source files with their specs pooled elsewhere. **Only carve-out:** a suite spanning several units (an e2e/HTTP suite) cannot live inside one unit's folder without misrepresenting its coverage — it sits at the **layer root** as `<subject>.e2e.spec.ts`. Enforced by the workspace ESLint file-layout law, and the enforcement is **probed both ways** (a deliberately flat logic file MUST fail). _(Ported 2026-08-08 from the Aysar canon `U22`+`U18`, renumbered — Aysar's IDs collide with this file's. U20 stands and is amended by this rule at the leaf.)_

- **U27 — The event chain is complete in BOTH directions, and it is declared in one catalog.** Every state-changing action **publishes** a typed domain event — and, **before** any new action is written, the existing catalog is audited for events that action should _react_ to. A feature that only emits, or only listens, is half-wired. Concretely: **(a)** backend writes emit through the transactional Outbox in the same tx (MS3), never a bare publish; **(b)** frontend mutations publish a typed event on the `EVENT_BUS` in `onQueryStarted` **after** success (W4), and subscribers invalidate — RTK tags handle same-module refresh, the bus handles cross-module reactions; **(c)** every event, backend **and** frontend, is declared **once** in the **`EVENT_CATALOG`** in `libs/contracts` with its payload schema, its producer, and its declared consumers — a duplicated or undeclared event name is a U3 violation; **(d)** an event with **zero** consumers is a plan finding, not an accident: the entry MUST carry an explicit `consumers: []` **plus a stated reason**, so an orphan is a deliberate, reviewable choice; **(e)** a phase is not done until its new actions appear in the catalog **and** its plan lists which _existing_ events the new module subscribes to. **NEVER** add a write path without asking what must now happen elsewhere. _(Owner directive, 2026-08-08: "each action should publish an event bus, so any other action can listen to it… any action we are adding, we should see if there is an event this action should work when this event happened, so the chain of the event bus is not missing any existing action.")_

- **U28 — Decide; ask the owner only when genuinely blocked.** **NEVER** put a question to the owner for a choice the plans, the rules, the code, or ordinary engineering judgement already answer. A question is warranted **only** when the answer is the owner's alone — product scope, a business or legal policy, a spend/credential decision, or two readings that lead to materially different products — _and_ when building under either reading would waste the work. Everywhere else: **choose**, state the choice and its reason in the deliverable (plan, PROGRESS entry, or code comment), and build. A choice made this way is **always** the option that implements the feature completely — no missing pieces, no gaps, no deferred halves. This is U0 applied to decisions rather than to code: _"the smaller option" is never a reason_, and a set of options that differ only in how much is left undone is a question that should not have been asked. _(Ported 2026-08-08 from the Aysar canon `U21`, renumbered.)_

- **U29 — A feature is not finished until the RUNNING environment is running it.** A phase ends with **restarting whatever is already up** — the Docker dev stack, any host dev server, any watcher — so the owner opens the app and sees the code that was just written, never the code that was running before it. Why this is law and not a habit: a dev server is **not** a live mirror of the repo. Watch mode recompiles _source_, but a **config** is read once at start — `tailwind.config.ts` and the `libs/config` preset it spreads, `vite.config.ts`, `postcss.config.cjs`, `eslint.config.mjs`, `nx.json`, `.env*`, a compose mount — and none of them is watched; a dependency added to `package.json` is not installed inside a container built before it. The resulting failures do **not** look like staleness: a new design token silently compiles to **nothing** (a colour "doesn't work" and the next hour debugs correct code), and an `@apply` of a token the loaded config never heard of is a **hard PostCSS error** reported against a file that is right. **Corollary:** a bug report from a running app is evidence only **after** that app has been restarted on the current tree, and a phase's "verified by looking" (U21e) against a server started before the work **does not count** and must be re-run. _(Ported 2026-08-08 from the Aysar canon `U23`, renumbered.)_

- **U30 — Never do irreversible work you cannot prove is still correct; a cache is an optimization, never a dependency.** Two halves of one discipline. **(a)** Before any destructive or one-way step — a migration that drops or rewrites data, a bulk update, a soft-delete sweep, a merge of duplicate rows, an overwrite of a published artifact — **re-read the current state and prove the precondition still holds**, inside the same transaction where possible; a check made minutes earlier is not a check. Irreversible work ships with the query that proves it was safe, recorded in PROGRESS. **(b)** A cache (Redis, an in-memory TTL, a resolved-credentials fingerprint) may only make a correct system _faster_ — the system MUST produce the same answer with the cache emptied, and a write is **NEVER** acknowledged on the strength of a cache alone. A cold cache is a supported state, not an incident. _(Ported 2026-08-08 from the Aysar canon `N25`+`N27`, merged and renumbered.)_

- **U31 — Context is a budget; the process reads only what it needs.** The startup reads are law (`docs/rules.md`), ledger (`docs/PROGRESS.md`), and **only the current phase's section** of `docs/plans/02-mvp.md` + its deep plan. **NEVER** read a whole plan to find one phase, and **NEVER** read `docs/PROGRESS-archive.md` or `docs/rules-changelog.md` at startup — they are archives, grep them on demand. **(a)** `docs/PROGRESS.md` is the live ledger only: a session entry is **≤15 lines** (what shipped, what it decided, what is NEXT), depth belongs in the module's `<module>.md` or the phase plan, and when a phase closes its entries move to the archive so only the newest two remain. **(b)** Sub-agents (`verifier`, `boot-verifier`, `designer`, `planner`) are handed a **distilled brief** — phase ID, "Done when", changed projects, rule IDs in scope — and **NEVER** re-read the law/ledger/plans the caller already holds; they grep one rule's text when a verdict turns on it. **(c)** History is never deleted to satisfy this rule — it is _relocated_ to a file nobody reads by default. (Owner directive, 2026-08-15: startup had reached ~155 K tokens and ~406 K per phase across three contexts, measured at an average 253 K of context on every API call. U13 is this rule's law-shaped half.)

## N — NestJS backend (per-service)

- **N1 — Base repositories.** All DB access goes through the shared enhanced base repositories (`libs/shared/database`), with a `Translatable` mixin for translatable tables. Per-model config declares `hidden`/`casts`/`appends`/`fillable`/`scopes`/`softDeletes`. **NEVER** ad-hoc queries in services.
- **N2 — Hidden fields & soft deletes.** Sensitive columns (e.g. `password`) declared `hidden`, stripped from output by default. Soft-deleted rows (`deleted_at`) excluded by a global scope; opt out only via `withTrashed()`.
- **N3 — DateTime service.** **NEVER** `new Date()` / `Date.now()` directly (ESLint `no-restricted-syntax`); use the timezone-aware shared DateTime service. DB writes are UTC; reads transform to the configured timezone.
- **N4 — Per-service own database + DDD layout.** Each service owns its **own database** (DB-per-service, MS5). Each module follows **presentation / application / domain / infrastructure** layering. **DTOs come from `libs/contracts`** (no local `dto/`). Raw SQL schema-qualifies table names.
- **N5 — Translation tables.** Any translatable column gets a dedicated `*_translations` table (locale-keyed); never store multiple languages in the base row. Single-item reads expose a per-locale `translations` map for edit forms.
- **N6 — In-service event bus + the network boundary.** _Within_ a service, modules may use an in-process event bus for side effects. _Across_ services, use RabbitMQ only (MS1–MS3). **NEVER** reach into another service's DB or import its code.
- **N7 — Validation & filtering.** Validate all input with Zod from `libs/contracts` via a `ZodValidationPipe`; request DTOs are `.strict()` (reject unknown keys). List endpoints accept **whitelisted, per-resource** filters via a shared `FilterSpec` — **NEVER** raw client column/operator passthrough. Boolean params use a strict `'true'|'false'` transform, never `z.coerce.boolean()`.
- **N8 — Auth & RBAC.** Email/password + JWT access+refresh + RBAC (roles & permissions) — owned by the **Identity service**. Other services trust the gateway-validated identity in the message headers (MS4); guards on every protected gateway route.
- **N9 — Envelope + errors.** A global response interceptor wraps payloads in the standard envelope `{ success, message, data, path, timestamp }`; a global exception filter standardizes errors (incl. Postgres error codes). Defined once in `libs/shared/util`, applied by every service/gateway.
- **N10 — Reproducible emit builds.** Gitignore `*.tsbuildinfo`; don't rely on `incremental` for emit builds. After `drizzle-kit generate`, verify migrations schema-qualify `pgSchema` enum types before applying.
- **N11 — NestJS apps are ESM + SWC (decorator metadata is load-bearing).** Every NestJS app is ESM (`"type":"module"`, `module:nodenext`) **transpiled by SWC** — `.swcrc` MUST set `transform.decoratorMetadata:true` + `legacyDecorator:true` + `keepClassNames:true` and `tsconfig.app.json` MUST set `experimentalDecorators`+`emitDecoratorMetadata`. **NEVER** transpile a Nest app with esbuild/tsx (they don't emit decorator metadata → Nest DI fails at runtime). `import 'reflect-metadata'` is the **first line** of `main.ts`. `tsc` is typecheck-only; SWC owns the runtime `dist`. Hand-roll the app (no `@nx/nest`/`@nx/node` generators) with explicit `nx:run-commands` `build`/`serve` targets; dev hot-reload = `swc --watch` (requires the **`chokidar`** devDep) + `node --watch`, `dependsOn:["^build"]` so lib `dist` exists first. Make controllers thin against an abstract-class seam so tests construct them directly (no DI metadata needed in vitest).
- **N12 — Import CJS-only packages by DEFAULT, never by name.** Under ESM (`type:module`, `nodenext`), Node's loader can't reliably expose a CommonJS package's named exports (`cjs-module-lexer` misses many), so a runtime `SyntaxError: does not provide an export named …` slips past typecheck (the `@types` declare names) and only bites at boot. For CJS libs (e.g. **`jsonwebtoken`, `argon2`, `pg`**) use a **default import** of the module object and read members off it (`import jwt from 'jsonwebtoken'; jwt.verify(...)`); take the type via a separate `import type { X } from 'pkg'`. Enable `esModuleInterop` in that project's `tsconfig` so the default import typechecks (ESM emit is unaffected — Node does the interop). vitest hides this (Vite pre-bundles), so a green test suite does NOT prove runtime imports work — **boot-verify** every new service.
- **N13 — Third-party integration secrets are encrypted-at-rest, server-side only, never in the settings table.** Any external-provider credential (R2/S3 keys, SMTP/SMS passwords, payment keys, API tokens) is **encrypted at rest with AES-256-GCM** (reversible — these are replayed to call the provider, never hashed) in a **dedicated non-public table owned by the settings-service** (`integration_secret`), the cipher master key from one env var (`APP_SECRETS_ENCRYPTION_KEY`; dev default, real key required in staging/prod). The ciphertext/iv/auth-tag columns are `hidden` (N2). They are **NEVER** stored in the settings/branding catalog (it resolves onto public endpoints), **NEVER** logged, and **NEVER** returned to a client — admin reads get a **masked status only** (`isSet/fromEnv/last4/updatedAt/updatedBy`), gated per-integration. A consumer resolves a decrypted secret **server-side only** via RMQ request/reply (`settings.resolve-secret`, MS2), resolution order **DB → env → null**. Until the vault exists, env is the bootstrap source **behind a single credentials seam** (e.g. media's `getStorageCredentials()`), so the swap is one place. (Canon: smart-restaurant `integration-secrets` + `secret-cipher.service`.)
- **N14 — The DB handle is injected ONLY into repositories; application services NEVER touch the database directly.** A service's constructor **NEVER** receives the `DRIZZLE` handle (or a `*Db`/`RepoDb` instance) — it depends only on **repositories** (N1) and other services, and all data access goes through a repository. For an **atomic multi-write** (e.g. a business row + its Outbox row in one transaction, MS3), the service depends on an injected **`TransactionRunner` / Unit-of-Work port** (a `scope:shared` seam in `@sanad/database`), **not** the raw `db`, and passes the yielded `tx` into the repositories (`repo.insert(tx, …)`, `outbox.enqueue(tx, …)`). The raw `db`/`tx` lives only inside **repositories + infrastructure** (the Outbox relay, the seed runner) — never the application layer. **Enforced by ESLint:** `no-restricted-imports` bans importing `DRIZZLE` from `@sanad/database` in `**/application/**/*.service.ts`. The `TransactionRunner` seam is implemented in `@sanad/database` when the first compliant service (P6) needs it (not scaffolded speculatively). **Pre-rule services that still hold `db`** (`content` lead + media-reconcile, `media` media, `settings` branding) are **grandfathered** with a tracked `eslint-disable` + `TODO(N14)` and refactored opportunistically — **every new service MUST comply.**

## MS — Microservices (the network boundary)

- **MS1 — Services never import other services.** Enforced by `@nx/enforce-module-boundaries` (`scope:*` tags). A service depends only on its own libs + `scope:shared`. A boundary-crossing import **must fail lint**.
- **MS2 — Cross-service reads = RMQ request/reply.** Use `@MessagePattern` over neutral query contracts in `libs/contracts`; the caller **MUST** add `timeout()` + `catchError` (request/reply has no built-in timeout). Exactly one responder per pattern. The gateway aggregates multi-service reads (API composition: `forkJoin`/`Promise.all` over `firstValueFrom`).
- **MS3 — Cross-service writes = events + Outbox.** Publish domain events with `@EventPattern`. A publisher **MUST** write the business row and the **outbox row in the same local transaction**; a relay publishes from the outbox. **NEVER** dual-write to DB + broker directly.
- **MS4 — Gateway is the only public entry.** Clients talk only to the API gateway. The gateway validates the JWT once and **forwards identity (userId/roles) in RMQ message headers** — never the raw token. Internal services are not publicly reachable (network-isolated). Sensitive services may re-validate (defense-in-depth).
- **MS5 — Database-per-service.** Each service owns its DB + its own Drizzle config + migrations folder; **NEVER** a shared DB or cross-service join. If services share one Postgres instance (dev), each uses a **distinct database** (or distinct `migrations.table`/`schema`) to avoid the Drizzle `__drizzle_migrations` collision.
- **MS6 — Idempotent consumers + safe delivery.** Consumers **MUST** be idempotent (record processed message IDs in the same tx as the business update). Use **manual ack** (`noAck:false`), **durable** queues + **persistent** messages, a sensible `prefetchCount`, and a **dead-letter queue + retry counter** (never infinite requeue).
- **MS7 — Sagas for multi-service writes.** Any workflow spanning services uses a **saga** (choreography first) with **compensating actions** — never 2PC, never assume ACID across services. Accept eventual consistency; design compensations to be idempotent.
- **MS8 — Observability & lifecycle.** Propagate OpenTelemetry trace context through AMQP headers. Every service exposes **liveness + readiness** (`@nestjs/terminus`), calls `app.enableShutdownHooks()`, and **drains in-flight RMQ messages on shutdown** (cancel consumer, bounded timeout) for zero-downtime rollouts.
- **MS9 — Incremental extraction.** Domain logic lives in `libs/` with `scope:`/`type:` tags. A new service is created by promoting a **stable** lib to an app once its boundary has held — not speculatively. Don't over-split (avoid the distributed monolith).

## F — Frontend (website + both portals)

- **F1 — One API layer, one envelope contract.** All server calls go through a central client whose base layer **unwraps the `{ success, message, data }` envelope** and extracts the standard error message in ONE place. Token refresh + auth header live there too. Match the backend's **real** refresh path/body (`POST /auth/refresh { refresh }` — verify, U15).
- **F2 — Loading is a skeleton; empty NEVER flashes during load.** Default loading affordance is a **skeleton shaped like the content**. Render-gate order is ALWAYS `loading-or-refetching → error → empty → data`; never let undefined/stale data fall through to the empty branch. Spinners only for the infinite-scroll tail and in-button mutation-pending.
- **F3 — Every list/detail ships explicit skeleton, empty, and error states** — from the shared component set, not ad-hoc.
- **F4 — Single-flag toggles are optimistic; tracking is fire-and-forget; only list-shape changes invalidate.** A boolean flip patches the cache optimistically, awaits, reconciles, rolls back on error — never refetches the whole list. Analytics/tracking is fire-and-forget, never invalidates or surfaces errors. Invalidate/refetch only for create/delete/reorder.
- **F5 — Freshness is event-driven.** Any view showing server data **subscribes** (client event bus) to events that could mutate it and refetches; a view with local pagination resets its buffer on the event. Cross-view sync goes through the event bus, not tag invalidation alone.
- **F6 — Forms are schema-validated.** A form library + a **Zod schema** (U16); messages are **i18n keys**; a user-action value-set marks the form dirty, a system/server prefill does not.
- **F7 — Settings reads are null-safe to the leaf.** Every settings access is optional-chained at EVERY level with a real coded default: `settings?.a?.b?.c ?? DEFAULT`. The compiler will NOT catch a missing group (stale cache, un-deployed backend, disabled group, first-paint gap). The default equals the backend's coded default (U9).
- **F8 — Display formatting via shared helpers.** Date/time/number/currency/phone display comes from **shared, locale- and settings-aware** format helpers that cache their formatter instances. **NEVER** inline `Intl.*`, `toLocale*`, or a date library at a call site.
- **F9 — Reuse before create.** **Actively search** the shared component library before writing ANY component; a missing primitive is added to the shared lib first, never inlined as a duplicate.
- **F10 — The shell owns chrome.** Header/nav/system chrome is defined ONCE at the shell/layout level; views never re-render their own header. Documented full-screen/wizard exceptions only.
- **F11 — In-app settings beat the device.** The app's persisted language/direction/theme is authoritative and **overrides** device locale, OS RTL, and system color scheme (except a sensible first-launch default).
- **F12 — Critical-path state seeds the first frame synchronously.** Theme, language, direction seed their initial value from a synchronous storage read at module load — never async hydration alone.
- **F13 — i18n is per-module, parity-checked, registered eagerly.** Each module owns `i18n/{ar,en}.json`, merged at module-**import** time (not in an effect). Key trees identical across locales (verifier-enforced). Brand/canonical strings come from a single source.

## OPS — Deployment & environments

- **OPS1 — `APP_ENV` drives all config.** Three environments — `development`, `staging`, `production` — selected by **`APP_ENV`**, never `NODE_ENV`. Each app has `.env.development` / `.env.staging` / `.env.production` (+ a committed `.env.example`); real env files are gitignored.
- **OPS2 — Dev runs in Docker with hot-reload.** The dev stack (`infra/docker-compose.dev.yml`) runs every service + per-service Postgres + Redis + RabbitMQ + nginx with **bind-mount + watch** so code edits hot-reload **without rebuild/restart**. The dev stack mirrors staging/prod topology.
- **OPS3 — Self-hosted infra, in-stack.** Postgres, Redis, and **RabbitMQ** run as our own containers in all environments — no managed/third-party broker. nginx terminates TLS with **acme** (Let's Encrypt). DB backups are produced by scripts and pushed to **Cloudflare R2**.
- **OPS4 — Never bypass the gate; it runs in three layers.** (1) **pre-commit** — `lint-staged` (eslint --fix + prettier) on staged files. (2) **pre-push** — `nx affected --base=<the remote sha git puts on the hook's stdin> --head=<local sha> -t typecheck lint test`: **affected-scoped, and `build` is deliberately NOT here**; it self-guards on OPS5 and falls back to the FULL gate when no base can be determined (never to "nothing"). (3) **`.github/workflows/ci.yml`** — the complete `nx run-many -t typecheck lint test build` on every push to `main` and every PR. **CI reports, it does not block** (no branch protection, by owner decision), so **a red `main` is a stop-work, not a notification**. Never bypass any layer (`--no-verify` forbidden). Deploys go through the `infra/scripts/deploy.sh` flow (migrate → build → health-check → rollover), staging before production.
- **OPS5 — NEVER run host `nx`/`nx run-many` (incl. the `verifier` agent) while the dev Docker stack is UP.** **(Largely SUPERSEDED 2026-07-18 by OPS8 — the six backend containers no longer run `nx serve` at all, so the backend `serve → serve` wedge is designed out; only `libs-builder` + the two frontends still run Nx, each on an isolated `.nx` volume. Running host `nx run-many` while the stack is up is still discouraged, and the recovery below still applies to those three, but the chronic backend cascade this rule guarded against is gone.)** Each app container runs its own `nx serve` against a per-service `.nx` named volume; a concurrent host `nx` invocation trips **"Recursive task invocation (`serve -> serve`)"**, which **wedges that service's `serve` inside its CMD** (Docker still shows it "Up", `restarts=0` — it hides) → no RMQ consumer → every cross-service call returns **HTTP 500 "Upstream service error"** (login, settings, even public branding). **`npx nx reset` does NOT fix it** (the state lives in the `sanad-dev_<svc>_nx` named volume). **Sequence instead:** run the `verifier` (host `nx run-many`) with the stack **DOWN**, then bring it UP for `boot-verifier`; for ad-hoc host checks use `npx vitest` / `npx tsc` / `npx eslint <file>` directly, not `nx`. **Recovery if wedged:** `docker compose down` (no `-v`) → remove the `*_nx` volumes (`docker volume ls --format '{{.Name}}' | grep '_nx$' | xargs docker volume rm`) → `up -d` → purge stale `<svc>.commands` queues. (See memory `dev-stack-ops`.)
- **OPS6 — nginx MUST forward the FULL client Host (with port) to the Next.js website — Server Actions' same-origin check.** Any nginx serving the website (dev + staging/prod) MUST set `proxy_set_header Host $http_host;` **and** `proxy_set_header X-Forwarded-Host $http_host;` — **NEVER** plain `$host` (it strips the port). Next.js validates every **Server Action** POST (form submits) by comparing the browser `Origin` to `x-forwarded-host`/`host`; a mismatch (dev `Origin: localhost:8190` vs forwarded host `localhost`) aborts with **`Invalid Server Actions request` → HTTP 500 on EVERY form submit** (the contact form AND the request-a-project form — the client-side form + gateway are fine; the action is rejected before it runs). Confirm by driving a real submit through nginx (not just a direct `POST /api/leads` curl — that bypasses the action). The **P9 prod nginx** must carry the same headers for the real domain.
- **OPS7 — After editing a single-FILE Docker bind mount, RESTART the container — a `reload`/HMR is NOT enough.** A mount of an individual file (e.g. `./nginx/dev.conf:/etc/nginx/conf.d/default.conf:ro`) pins that file's **inode**; the editor writes-new-then-renames (atomic replace), changing the inode, so the container keeps seeing a **stale/truncated** view of the file (symptom: `nginx -t` → `unexpected end of file, expecting "}"`, or the container's `wc -l` < the host's). `docker restart <svc>` (or `up -d --force-recreate <svc>`) re-resolves the mount to the current host file. Where feasible, mount the **directory**, not the single file.
- **OPS8 — The dev BACKEND containers run a crash-restarting supervisor, NOT `nx serve`; ONE `libs-builder` container is the SOLE writer of `libs/*/dist`; every app container carries `restart: unless-stopped` + a liveness healthcheck.** This is the durable replacement (2026-07-18) for the chronic dev-stack fragility (OPS5's cascade + `node --watch` staying dead + the recursive-task wedge). The invariants — do not regress any of them:
  - **No Nx in a backend container.** The gateway + five services run `infra/scripts/dev-entry.sh` → SWC compile → `infra/scripts/dev-serve.mjs`, a supervisor that respawns `node dist/main.js` on **any** exit (crash or clean) and restarts it on dist changes. `nx serve` (which re-enters the task graph → `serve → serve` wedge) and bare `node --watch` (which stays dead after a non-zero crash — the "Failed running 'dist/main.js'" symptom) are both banned in containers. Migrations run directly (`node dist/db/migrate.js`), never `nx db-migrate` (its `^build` rebuilt shared libs).
  - **`libs-builder` is the ONLY writer of the shared `libs/*/dist`** (`infra/scripts/dev-libs.mjs`): it builds every shared lib once, marks itself healthy (`.nx/.libs-ready`), and rebuilds only the changed lib on a src edit. **The marker MUST be deleted at startup, before the first build:** it lives in a named volume that survives `compose down`, so a stale marker makes the healthcheck green instantly and `depends_on: service_healthy` releases every service **before** the rebuilt dist exists — the N12 boot failure this gate is meant to catch, arriving as a mystery `does not provide an export named …`. Measured 2026-08-09 (P8.7 boot-verify): healthy at +9s, build finished at +21s. Every app/frontend container `depends_on: { libs-builder: service_healthy }`. **Never re-introduce `dependsOn:["^build"]` into a container's serve path** — a service (re)start rewriting the shared dist is the whole cascade.
  - **Restart policy + healthcheck on every app container.** `restart: unless-stopped` makes a crash transient; a Node HTTP liveness probe (`/api/health` for the gateway, `/health` per service) gives real readiness (judge liveness by this + logs, never `docker ps "Up"`).
  - **File watchers MUST use directory-based watching + `usePolling: true`.** chokidar v5 **dropped glob support** (a `libs/*/dist` pattern matches nothing) and Docker Desktop macOS does **not** deliver native fsevents/inotify across the VirtioFS bind mount (a host edit or another container's write raises no native event). So every chokidar watcher in the dev scripts watches concrete dirs with a function `ignored`, and polls (`interval` ~400ms).
  - **Launch/stop via `infra/scripts/dev-up.sh` / `dev-down.sh` / `dev-health.sh`** (they assert `--env-file infra/.env.development` and sequence the boot via the health `depends_on`). The old `touch apps/<svc>/dist/main.js` / drop-`*_nx`-volume recovery playbook is obsolete for backends.

- **OPS9 — This machine is a shared 16 GB budget; never let one project take it all.** The Mac runs **three** projects against **one** Docker VM (sized 6 GiB, owner decision 2026-08-15), and host swap is what dies first. **(a) Every container declares `mem_limit`, and every Node container also declares `NODE_OPTIONS=--max-old-space-size`** — an uncapped V8 defaults to ~2 GB of old-space per process, and the dev stack runs ~21 Node processes. A new service **NEVER** lands without both. **(b) Bring up only the phase's compose `profiles`** (`infra/scripts/dev-up.sh core <profile…>`), never `full` out of habit; `--build` is opt-in, not the default. **(c) Host `nx` always runs `--parallel=2`** — the default 3, times a Vitest worker pool per project, put ~30 node processes on the host and made the gate _slower_ by swapping. **(d) The two spikes never overlap:** stack DOWN → full verifier → stack UP on a minimal profile → boot-verifier (OPS5 + U12b). (Owner directive, 2026-08-15: measured 15.5 GB of 16 GB swap in use with Sanad's stack already down.)

## DOC — Documentation

- **DOC1 — Every module has a synced doc.** Every backend service-module and every frontend feature-module has a colocated `<module>.md` (purpose, entities, contracts, events consumed/emitted, settings used). It is **updated in the same change** that modifies the module — a module change with a stale doc fails review.
- **DOC2 — One always-current, fully-documented Postman collection.** The repo keeps a single source-controlled Postman collection at **`docs/postman/`** (`sanad.postman_collection.json` + `sanad.postman_environment.json` + `README.md`) — the **complete, self-documenting map of every gateway endpoint** so a frontend dev integrates without reading backend code. Whenever a gateway route is **added, changed, or removed**, the collection is updated **in the same change** (a PR that touches an endpoint without it fails review). Every **folder** (one per domain) and every **request** carries a markdown `description` (purpose, auth + required permission, query/body shape with field rules, returns shape); requests that mint tokens/ids a later request needs include a `test` script capturing them into collection variables; routes are grouped into domain folders; request/response shapes mirror `libs/contracts` (U3/U15 — verify the shape, never invent it). Collection-level conventions (the N9 envelope, `{{baseUrl}}` through nginx, bearer auth, `{ar,en}` locales, `.strict()` bodies) live in the collection `info` description. New service ⇒ new folder.
