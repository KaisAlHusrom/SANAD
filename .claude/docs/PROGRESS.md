- 2026-06-24 — **Content architecture clarified (owner question — per-collection services vs one `settings` table).** The owner's Laravel reference stores all section content in ONE key-value `settings` table. Decision/rationale (no rule change): there are **two kinds of content**, stored differently — (1) **config / key-value** (branding, colors, toggles, contact) lives in the **settings-service** (P3, the direct analog of the Laravel settings table); (2) **rich relational content** (blog post + category + tags M2M + author + pagination + search + draft/publish + SEO slug, portfolio case studies, testimonials w/ ratings, team) needs typed schemas + relations + querying, which a key-value table can't do. Our model = the standard CMS shape (Strapi/Directus/WP custom-post-types): a flexible **page builder** (pages→sections→blocks, owner's decision — the "settings-like" free-form layer) **PLUS typed collections**; sections/blocks orchestrate layout, collections hold structured data (a "testimonials section" block references the testimonials collection). Per-collection is **scalable**: each is a thin ~12-file mechanical clone on a SHARED base (`LocalizedRepository`/`BaseRepository` + assembler + FilterSpec canon), mostly declarative (model-config + field lists), and **fully type-safe** (U3/U4/U15) — a generic config-driven "content-type engine" would cut files but force runtime-only/`any` typing, fighting our strict-typing rules. **Owner follow-up (optional):** review the Laravel `admin/pages/settings` + controllers to map each section → config (settings-service) vs rich content (collection / page-block) — pending the project path.
